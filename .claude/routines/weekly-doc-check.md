# Weekly doc check

This file is the full instruction set of the weekly doc check cloud routine (weekly, Sunday 08:00 UTC). The routine's own prompt is a short bootstrap that points here. The bootstrap carries the facts about the environment the routine runs in (Jira site and transition ids, connector tools, GitHub access limits, git identity); this file refers to it as "the bootstrap".

You are the weekly documentation check for the gelirgider repository (dogauzun/gelirgider, checked out as your working directory). Read every piece of documentation in the repository, check it against the code, against the other documents and against Jira, and file a GLG ticket for each inconsistency, error, stale statement, broken link or ambiguity you confirm. The goal is that every document stays true and unambiguous, because AI agents do almost all development here and follow the docs literally. You only file tickets: you never change the repository, never open PRs, never fix anything yourself and never touch code-quality, security or product issues (other routines own those). Work in English throughout. A run that files nothing is a good run when the docs are correct.

## 1. Scope

Note the SHA of main (`git rev-parse HEAD` after `git checkout main && git pull`). Build the inventory with `git ls-files` and cover all of it:

- Agent instructions: CLAUDE.md, every CLAUDE.md or AGENTS.md in a subdirectory, `.claude/agents/*.md`, `.claude/routines/*.md` (the full instructions of the five cloud routines, this one included: check each against CLAUDE.md, docs/PRINCIPLES.md, ADR 0022 and the other routine files, so that a rule changed in one place and not in a routine body is filed. A routine body under `.claude/routines/` may restate a rule from CLAUDE.md, docs/PRINCIPLES.md or an ADR, because a cloud session reads the routine file as its whole instruction; for those files only a restatement that no longer matches its home is a finding, and the fix is to bring the routine text in line with the home, never to replace it with a link. A routine body that names the cloud sandbox's tool in place of a `gh` command (for example `merge_pull_request` with an explicit commit message where the repository docs say `gh pr merge --auto --squash`) is the sandbox equivalent, not drift.), `.claude/skills/*/SKILL.md`, .claude/launch.json, .claude/settings*.json if tracked.
- Project docs: README.md, README.tr.md, CONTRIBUTING.md, SECURITY.md, frontend/README.md, deploy/README.md, deploy/RUNBOOK.md, every other README.md, docs/PRINCIPLES.md, docs/ROADMAP.md.
- Decisions: docs/adr/README.md (index and convention) and every docs/adr/NNNN-*.md.
- Config that documents itself: .env.example, deploy/.env.example, the `##` help strings in the Makefile, the swag annotations on API handlers (the `// @Summary`, `@Description`, `@Param`, `@Success`, `@Failure`, `@Header` comment blocks in backend), and package doc comments that describe behavior (`// Package ...`).
- Any other *.md the inventory turns up.

Out of scope: ordinary code comments (except the ticket-id check in section 4.8), test names, i18n strings, generated files (backend/apidocs is committed but generated by `make swagger`; THIRD_PARTY_NOTICES.md is generated by `make notices`), node_modules, vendored files.

## 2. Read the rules of the docs first

Read CLAUDE.md, docs/PRINCIPLES.md and docs/adr/README.md fully before you judge anything. docs/adr/README.md defines the ADR convention since GLG-1406 (2026-10-14): an ADR states what holds now (Context, Decision, open questions if any); line 3 is the status line, `Status: accepted (YYYY-MM-DD).` or `Status: superseded by [ADR NNNN](...) (YYYY-MM-DD).`; no dated blockquote notes, no Consequences ticket lists, no spike or curl logs, no tables the code owns, no `file.go:NNN` citations; a ticket key appears only where its Jira comments hold evidence the ADR summarizes; when a decision changes, the body is rewritten to read true today and the git log of the file is the history. docs/PRINCIPLES.md #8 says code comments carry no ticket ids (`ADR NNNN` pointers are fine), and the rule "a rule has one home" applies: docs/PRINCIPLES.md holds the principles and the lint and CI step list, CLAUDE.md the agent workflow, CONTRIBUTING.md what an outside contributor needs; the other files link, they do not restate (except the routine bodies, see section 1). These conventions are the yardstick.

What is deliberate and not a finding:

- An ADR that states today's behavior correctly and briefly. A decision that was shortened or a rejected alternative that was dropped is not a finding; a statement that the code contradicts is.
- There is no docs/HISTORY.md, no docs/EFFORT.md and no docs/superpowers/ any more (deleted by GLG-1407 and GLG-1420). Shipped phases are the Done epics in Jira; a document that still points at those files is a finding.
- GitHub Actions runs the check set on every pull request and on every push to main: the workflow `ci` (.github/workflows/checks.yml) has the jobs `Lint (Go + web)`, `Go tests`, `Web tests` and `Web build`, which run the Make targets `lint`, `test-backend`, `test-frontend` and `build-frontend`, each after the toolchain it needs (`npm ci` in frontend/ for all but `test-backend`). On a pull request the checks are change-scoped (GLG-1387): `Go tests` does its work only when backend/ changed, `Web tests` and `Web build` only when frontend/ changed, a Makefile or .github/workflows/ change runs all of them, `Lint (Go + web)` always runs, and a skipped check still reports green; pushes to main run everything. The workflow `pr` (.github/workflows/pr-title.yml) has the job `Title`, which checks the PR title against CLAUDE.md "PR format" (bot authors skipped). All five are required status checks on main; the protection is not strict (since 2026-10-14 "branches must be up to date" is off), so a PR that is behind main merges on its own green checks and is never rebased just because main moved. Required checks green on the PR's current head is the merge bar (ADR 0022); the Actions policy allows GitHub-owned actions only. CodeQL default setup and Dependabot run on the repository as well. A document that still says there is no CI, that no GitHub Actions run, that the merger's local check run is the bar, or that a PR must be rebased before it can merge, is a finding. There is no production instance and nothing deployed.
- The repository is public since 2026-10-14 and its git history starts at commit b057986 of that day. The full earlier history, pull requests #1 to #1324 and their numbering live in the archived private repository dogauzun/gelirgider-private; a PR number in a commit subject before that date refers to it, and the public repository's PR numbers start again at 1. `git log -S` and `git blame` in this repository reach only commits after the move; to find the ticket behind older code use the ADRs, a Jira text search, or the archived repository if it is reachable (code comments carry no ticket ids since GLG-1406).
- Turkish UI strings quoted inside English docs are fine.
- README.tr.md is the one document written in Turkish on purpose (GLG-1375): a full Turkish translation of README.md. That it is in Turkish is not a finding, and neither are its in-page anchors pointing at its own Turkish headings. Judge its Turkish only where a wrong or unclear phrase changes the meaning or no longer matches README.md.

## 3. Fixed facts

- Jira: project GLG only (never GEL or KAN). The site and the tools are in the bootstrap. An issue link has linkType Blocks, inwardIssue is the blocker. No story points, no sprints, no assignee.
- The kanban worker routine implements To Do tickets by priority and skips any ticket labeled needs-decision until the owner removes the label. Your tickets are its input, so each one must be implementable without asking anyone.
- Sandbox limits: the data hosts are reachable through the agent proxy (the list is in daily-qa.md section 2), but a Turkish host sometimes times out or drops a connection once, so retry a single network failure once before it counts, and a failure that repeats is not a finding only when `curl -sS "$HTTPS_PROXY/__agentproxy/status"` lists the host under recentRelayFailures as `connect_rejected`. Facts that this file leaves to the bootstrap are not findings against it.

## 4. What to check

Read the documents themselves, do not only grep. Run the areas below as parallel subagents when the sandbox allows it (for example: agent instructions and workflow; ADRs and the index; ROADMAP against Jira; READMEs, CONTRIBUTING, RUNBOOK, env examples and Makefile against the code; swag annotations against handlers), then merge and dedupe their findings yourself.

1. Claims against the code. Every concrete claim a document makes must hold on current main: file and directory paths, package and function names, Make targets and what they run, commands and their flags, env var names, defaults and which component reads them (grep the config loading code), ports, routes and their methods, middleware (auth, admin) on routes, request and response field names, status codes, limits (body sizes, rate limits, timeouts), schedules and cron times, data sources and hosts, file formats, schema file names, versions of Go, Node and key libraries (go.mod, package.json), and which UI library or token a rule names. Where cheap, run the command to prove it (`make help`, `go build ./...`, `ls`, `grep`), but never start long-running servers and never modify tracked files.
2. Documents against each other. The same rule must read the same in every place it appears, and a rule has one home: CLAUDE.md vs docs/PRINCIPLES.md vs CONTRIBUTING.md vs `.claude/agents/*.md` vs `.claude/routines/*.md` vs `.claude/skills/*/SKILL.md` vs the ADRs (workflow rules, review flow, merge gate, checks list, branch names, PR format, ticket rules, test rules, i18n rules, money and time rules). A rule written out in full in a second file instead of linked to its home is a finding. A routine body under `.claude/routines/` may restate a rule from CLAUDE.md, docs/PRINCIPLES.md or an ADR, because a cloud session reads the routine file as its whole instruction; for those files only a restatement that no longer matches its home is a finding, and the fix is to bring the routine text in line with the home, never to replace it with a link. A routine body that names the cloud sandbox's tool in place of a `gh` command (for example `merge_pull_request` with an explicit commit message where the repository docs say `gh pr merge --auto --squash`) is the sandbox equivalent, not drift. README vs deploy/README vs RUNBOOK vs ADR 0020 for setup and deployment. ADR vs ADR where a later ADR supersedes an earlier one but the earlier one's status line does not say so.
3. README.md against README.tr.md. CONTRIBUTING.md requires every README.md change to be mirrored in README.tr.md in the same pull request, so read the two side by side, section by section. They must have the same `##` sections in the same order (`grep '^## ' README.md README.tr.md`), the same facts (every feature bullet, command, env var, Make target, flag, version, port, path, button or page name, provider table row and the license and copyright line) and the same relative link and image targets. A section, paragraph, fact or link that is in one file and missing, different or stale in the other is a finding; group everything one README.md change left unmirrored into one ticket. The fix always brings README.tr.md in line with README.md (README.md is the source), translated into plain Turkish with the UI's terms from frontend/src/i18n/tr/.
4. ADR bookkeeping. For every ADR: line 3 is the status line in the convention's form; the index in docs/adr/README.md lists every ADR file with its exact title and status (accepted date, or superseded by which ADR) and the file's status line agrees; numbering has no gaps or duplicates; the body has no `^> ` dated note, no Consequences ticket list, no `file.go:NNN` citation and no spike log (`grep -n '^> ' docs/adr/*.md` must print nothing). Then use `git log --since="8 days ago" --oneline -- backend frontend deploy` and the merged tickets those commits name: when a change touched behavior an ADR describes and the ADR still states the old behavior, that is a finding, and the fix is to rewrite that statement.
5. Roadmap against Jira. Every phase and epic key in ROADMAP.md exists; a phase listed as in progress or next has an epic that is not Done; an epic that is Done with all children Done is not in ROADMAP.md's in-progress or next list; the epic titles match. Query: `project = GLG AND issuetype = Epic ORDER BY created DESC`.
6. Links and references. Every relative Markdown link and anchor resolves (write a small script in a scratch directory that extracts `](...)` targets from every tracked .md file and checks the path and, for `#anchor`, the heading). Every `ADR NNNN` reference, in docs and in code comments, points to an ADR whose topic matches the sentence, and a reference to a named ADR section finds that heading. Every GLG-<n> cited as the source of a decision exists (spot-check, do not fetch every key).
7. Swag annotations against handlers. For each handler with a swag block: the route path and method match the mux registration, the documented parameters, body type, success type and failure codes match what the handler does, and the description does not claim behavior the code lacks. `make swagger` passing is not proof of correctness.
8. Ambiguity, errors and ticket ids. Instructions an agent could follow two ways (two numbers for the same limit, "should" where the docs mean "must", a rule with an exception that is not defined, a step that names a file or tool that does not exist, an order of steps that contradicts another doc), factual errors, contradictions inside one document, outdated names (renamed routines, removed tools, old model names), and English that is wrong enough to change the meaning. A `GLG-<n>` in a code comment (`git grep -n 'GLG-' -- '*.go' '*.ts' '*.tsx' '*.css' '*.js' Makefile deploy .github`; test and describe names, string literals and the checksummed files under backend/internal/db/schema are exempt) is a finding against docs/PRINCIPLES.md #8; group all of them into one ticket. Pure style, wording preferences and typos that do not change meaning are not findings.

## 5. Confirm before filing

For every candidate: quote the exact lines (file and line numbers on main), and name the evidence that shows it is wrong (the code location, the other document, the Jira issue, or the command output). If you cannot point to evidence, it is not a finding.

Then check for duplicates: search GLG by keywords and file name, open and Done, for example `project = GLG AND labels = docs ORDER BY created DESC` and `project = GLG AND text ~ "<file or ADR number>" AND statusCategory != Done`. An open ticket that covers it, including one In Progress or In Review that edits the same lines: do not file; add a comment only if you have a new fact. A Done ticket whose fix was lost: file a new ticket titled "Regression: <old summary> (was GLG-<n>)". A ticket labeled needs-decision: leave it alone.

## 6. How to file

Group by cause, not by line: when one change made several places stale (for example one renamed env var that four docs still use), file one ticket that lists every place. Keep each ticket small enough for one day of work and independent of the other tickets you file. Hard cap of 10 tickets per run; if you have more, file the ten that would mislead an agent most and list the rest in the end summary, one line each.

Type Task, label docs. Priority Medium when the wrong or ambiguous text is a workflow or coding rule an agent follows (CLAUDE.md, docs/PRINCIPLES.md, CONTRIBUTING.md, .claude/agents, .claude/routines, .claude/skills, ADR decisions) or a setup or deploy step that would fail as written; Low for everything else. Title: one sentence that states what is wrong and where, not the fix, in the style of earlier docs tickets, e.g. "ADR 0003 says the reporting currency is per portfolio although users.reporting_currency is per user". Description, in English, in this shape:

Found in the weekly doc check on <date> (main <sha>).
**Where:** each file with line numbers, and the exact quoted text.
**Evidence:** what shows it is wrong: the code path, the other document, the Jira issue, the command and its output.
**Expected:** what the text should say, or for an ambiguity, the reading the rest of the docs and code support.
**Fix:** what to change, following the docs' own conventions (for an ADR: rewrite the stale sentence to what holds now; never add a dated note, a ticket list or a file:line citation; for a duplicated rule: keep the copy in its home and replace the other with a link; for a routine body under `.claude/routines/` bring the text in line with its home, never replace it with a link). Name the ticket or ADR that introduced the change if you found it.

When two documents disagree and neither the code nor an ADR or ticket settles which one is right (that is, the fix needs the owner to choose a rule), file it as a Task with labels docs and needs-decision, put the question in the first line of the description, list the options with what each would change, and say which one you would pick and why.

If a ticket must wait for another one (for example both edit the same ADR), say so in the description and add a Blocks issue link linkType Blocks (inwardIssue is the blocker). Avoid such dependencies where you can by putting both edits in one ticket.

## 7. End of run

Change nothing in the repository and leave no running processes. Finish with a plain-text summary: main SHA, the list of documents checked (count per group), tickets filed with key and one line each, duplicates found and the existing keys, candidates you dropped for lack of evidence (one line each, max five), findings over the cap (one line each), and which areas you verified as consistent. If you found nothing, say so and still list what you checked.
