# Architecture decision records

An ADR records a decision that later work has to follow and that the code
alone does not explain, such as a data source chosen in a spike, the design
of a phase epic, or a workflow rule. A phase epic's planning ticket writes a
new ADR, or amends the existing ADR when that one still holds ("no new ADR" in
the roadmap), and a retro ADR (0019 to 0021) records decisions that were made
earlier and only lived in the code or the roadmap.

## Amendment convention

The status paragraph starts on line 3 and is wrapped at the file width:
`Status: accepted (GLG-n, YYYY-MM-DD); amended YYYY-MM-DD (GLG-n, short note); ...`.

The body is history and is not rewritten. When a place in it goes stale, a
dated blockquote goes under its paragraph, for example
`> Superseded YYYY-MM-DD by [ADR NNNN](NNNN-file.md) (GLG-n): what holds now.`
The `by [ADR NNNN](...)` part is there only when another ADR made the change.
There are four kinds of note: `Superseded` (the text no longer holds),
`Amended` (the decision was extended), `Resolved` (an open question got its
answer) and `Correction` (the text was never true). The date is the date the
change happened: the Europe/Istanbul local date of its merge commit. The
status paragraph lists the tickets that edited the ADR's own text, that is,
amendments written into the body. A ticket that
only edits the text inside a note another ticket wrote is not an amendment
and is not listed there. A `Superseded`
note made by another ADR is a partial supersession: it goes on the status
paragraph, in date order with the amendments, as
`superseded in part by [ADR NNNN](NNNN-file.md) (GLG-n, YYYY-MM-DD): what holds now`
(ADR 0015's form), and that ADR goes in the "Superseded in part by" column of
the index above. Any other note marks a place that later work elsewhere made
stale, so its ticket is named in the note; the ticket may also appear in the
status paragraph, and then in the Amended column, but does not have to. ADR
0001, 0004 and 0015 also put a larger amendment in a dated section at the end,
and their status paragraph points to it.

A new decision that replaces an old one gets a new ADR, and the old ADR gets a
`Superseded` note that links to it. A new ADR takes the next free number and
follows the section shape of the recent ones: Context and Decision, then
Recorded simplifications and Consequences where there are any.
